## Inspect an export first

```bash
python scripts/record3d_inspect.py "<export folder or .zip>" --measure
```

Writes `inventory.json` and `inventory.md` under `runs/lidar_inspect/<name>-<time>/` (git-ignored). The source is
opened read-only. Nothing is extracted unless `--copy <new folder>` is given (then with a SHA-256 manifest; the
target must be a new folder outside the export).

What the report decides, and how strictly:

- **available** – measured in the files (e.g. PLY headers, image headers, point statistics).
- **candidate** – something *looks like* the needed information (a JSON key named like intrinsics, 16-bit images
  that may be depth) but its meaning is unverified. A candidate is never used as if it were verified.
- **missing** – not present.

Routes (`paths` in the report) list what each needs and what is missing; a coloured point cloud alone is never
treated as a calibrated RGB-D dataset, and per-frame clouds are never fused unless they are shown to share one
coordinate frame.

| Finding | Evidence |
|---|---|

| 1662 complete members `0000000.ply … 0001661.ply`; `0001662.ply` cut off at the end | sequential local-header scan (25 s, 153 MB peak RAM) |
| binary little-endian PLY, `x y z red green blue reserved`, 181k–294k points per frame (454 M total, 7.3 GB uncompressed) | PLY headers; header comment "Generated by HEGE.SH 1.10" |
| no normals, no RGB images, no video, no depth images, no metadata / poses / intrinsics in the zip; `sound.m4a` beside it | file inventory |
| frames are **sensor-relative**: all 12 sampled frames (spread over the sequence) have centroids ≈ (0, 0, −0.9 … −1.6), nearest points 0.8–1.1 m from the origin, centroid drift 0.23 m | `--measure` (200k-point samples per frame, read in memory) |
| extents ≤ 2.2 units per frame: consistent with metres, still to be confirmed with one known length | `--measure` |

Consequences:

1. The frames cannot be merged into one room as they are (`lidar_point_mesh` is refused for this export).
2. Without per-frame camera poses the clouds can be registered only by ICP (drift-prone, weak on plain walls), and
   without RGB frames + intrinsics they cannot be photo-textured.
3. Least disruptive next steps, in order: (a) copy the export again and check the zip opens (compare its size with
   the phone's); (b) export the capture again in a form that also includes per-frame camera poses and the RGB frames
   / video, if the app offers one for this capture – then inspect it with this tool before any processing; (c) add a
   normal RGB video or photos of the room for the photo pipeline (and later LiDAR scale); (d) only then consider
   ICP registration of the PLY frames.

## Memory and disk for large LiDAR sequences

- 454 M points loaded at once would need ~11 GB (xyz + colour + normals): never done. Sequences are fused frame by
  frame into a voxel grid (`VoxelAccumulator`): memory follows occupied voxels (a room surface at 1 cm ≈ 1–3 M).
- Damaged-zip scans keep ≤ 64 KB per member (headers only); measured samples are read one member at a time.
- Poisson meshing checks its estimated RAM against what can be planned (`hardware.plannable_ram_gb`) before running.
- A working copy of this export would need ~2.7 GB (zip) or ~7.3 GB (extracted): put it on a local folder, not in
  OneDrive.

## Polycam: finished mesh import (implemented) and raw keyframes (on hold)

**Import a finished mesh** (Polycam "GLTF" export, a zip with one `.glb`):

```bash
python scripts/studio_cli.py import-mesh --title "Room (Polycam scan)" --from "GLTF polycam.zip" --root projects
```

`namma.studio.mesh_import` copies the GLB unchanged into a Studio project and run, detects the floor (lowest large
horizontal surface; +Y up as glTF requires), picks a start point with the most clearance, builds the roaming grid and
an unverified navigation candidate, writes an honest quality report ("geometry and textures by Polycam") and an
IF-13 1.2.0 package with scale `device_tracking`. Tests: `tests/test_mesh_import.py` (synthetic rooms).

Result for the 2026-10-21 Polycam scan: 19,514 triangles, one 4096×2976 texture, 6.97 × 3.10 × 5.46 m, floor found
1.51 m below Polycam's origin, 68 % floor coverage, 9.6 m² unverified walkable floor; viewer e2e 9/10 (V-07 "jump to a
photo viewpoint" fails by design: the mesh export has no photo positions). The mesh itself is fragmentary (189
separate pieces, ~36 % of a closed room's surface): Polycam scanned mostly from one spot.

**Raw keyframes** ("Images" export: 78 keyframes with photo, 256×192 depth maps (not LiDAR: iPhone 14), confidence, intrinsics and a 3×4
pose each): ON HOLD. The stored poses could not yet be reconciled with the depth (best convention: 21–26 % of
neighbouring-frame depth agrees within 5 %; > 80 % expected) nor with the GLB (median 57 cm off). Next diagnostics:
register keyframe depth to the GLB without the stored poses, and render the GLB from a stored pose against its photo.
