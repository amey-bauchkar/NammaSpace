Namma Space – Technical Abstract (Round 1: 3D Reconstruction & Roaming)

Techfest IIT Bombay 2026–27 · Team Namma Space · Draft generated 2026-10-11 from the repository evidence. All performance and accuracy figures below come from recorded runs (files named in each table); none are estimates.

1. Problem and scope

Namma Space turns ordinary phone photos or one video of an indoor space into a photo-textured 3D model that anyone can walk through in a web browser, without installing software and without manual 3D modelling (OFF-14…16, OFF-23/24). Round 1 asks for an SOP, a reconstruction pipeline and a free-roaming web viewer. Our design constraint is the team's real hardware: a laptop with an Intel Core 5 120U, 16 GB RAM, integrated graphics and no CUDA, so every core step runs on the CPU, locally, with no paid API or cloud service.

2. System architecture

 phone photos / video ─► Studio (local web app, 127.0.0.1) ─► capture check ─► worker process
   worker: prepare ─► COLMAP SfM (CPU) ─► undistort ─► OpenMVS dense ─► mesh ─► texture (GLB, embedded)
          ─► model frame (floor, up, start view, collision grid) ─► quality report ─► IF-13 scene package
 viewer.html (three.js) ◄── verified package (SHA-256 per file)      publish ─► static website / ZIP
  • Studio (Python standard-library HTTP server + worker processes): project folders with JSON manifests, no database; one memory-heavy job at a time; every stage is resumable (completed stages are kept after a crash, a cancel or an out-of-memory failure).
  • Contracts: the scene package (IF-13) states the model frame (right-handed, +Y up, floor at y = 0) and an explicit scale status. Photos alone cannot fix real-world scale, so the default is unknown; a user can add one known length later (no markers or tape required).
  • Viewer: three.js, vendored (no CDN dependency); loads a light level of detail first, then full detail; every file is hash-checked before use; failures show a clear message instead of a broken scene.

3. Reconstruction pipeline

Stage Tool / method Why
Capture check OpenCV / Pillow: sharpness (Laplacian variance), exposure, exact and near duplicates, ORB overlap graph; video: 3 frames/s, sharper of each pair (deterministic, FFmpeg) Catch bad captures before minutes of processing
Camera poses COLMAP 4.2.1 (CPU SIFT, exhaustive matching for photos, sequential for video, incremental mapping + second registration pass) Robust, BSD-licensed; threads chosen from free RAM; guided matching disabled after it reached 9–10 GB
Dense geometry OpenMVS 2.4.0 DensifyPointCloud (≤ 1600 px Preview, ≤ 2560 px Standard) on an evenly spread, sharpest-in-bin subset of ≤ 90 / ≤ 140 placed images Best CPU-only MVS available to us; tracking needs dense video frames, surfaces do not
Surface OpenMVS ReconstructMesh (a tested edge-length cleaning step was not adopted: it removed real flat surfaces) Watertight-leaning surface from the dense points
Texture OpenMVS TextureMesh → GLB; textures embedded as JPEG, local paths removed, seam levelling off (it blackened 17–34 % of texels in this build), neutral grey where no photo sees a face Self-contained, portable, honest output
Model frame Floor plane (RANSAC, scale-free tests on camera heights) or camera-orientation fallback; start view = the capture photo that overlooks most of the scene The viewer opens at eye height, looking into the room
Quality Registration rate, reprojection error, floor coverage, mesh fragmentation, textureless photos, unknown scale Every warning is shown to the user in plain language

Two processing profiles: Preview (fast, 1600 px) and Standard (full-resolution photos with a memory cap, two levels of detail).

4. Capture SOP (summary of docs/CAPTURE_SOP.md)

Lights on; main 1× lens; JPEG ("Most Compatible") on iPhone; walk along the walls facing into the room, one step (~0.5 m) between photos, about two-thirds overlap; floor in the lower third of every photo; a second, lower lap around large furniture; 3–4 photos while passing each doorway; always include an edge or object when photographing plain walls, glass or mirrors; 60–150 photos per room, or one slow 1–3 minute video. The Studio's capture check enforces the limits (10–300 photos, one video, JPEG/PNG, ≥ 480 px) and explains every warning.

5. Web viewer

First-person controls: click to capture the mouse (pointer lock) or drag to look; W A S D / arrows to walk; Shift to run; F toggles fly mode; R resets to the start view; [ ] jump through the original photo viewpoints. Walking keeps the camera at the capture eye height inside the free space connected to where the photos were taken (reconstructed furniture and walls block; floater specks do not). Floor areas the photos did not reconstruct are shown by a faint, labelled guide grid instead of a void or invented geometry. Place labels can be added by clicking on the model and found by search (jump transition). Walking paths are shown only as unverified guidance (Round 2 scope).

7. Limitations and next steps

  • No own-home capture yet. Round 1 asks for the team's own home (OFF-34); every figure above uses public datasets. The SOP is built for the iPhone 12 but has not been validated with it.
  • Completeness depends on the room. Textured, cluttered spaces reconstruct well (held-out delivery_area 0.61); plain white walls, desks and dark floors stay partly missing (held-out office 0.30–0.33). Missing floor is shown by a labelled guide grid and reported, never filled with invented geometry.
  • Fast handheld video fails. On both held-out iPad videos CPU structure-from-motion placed only 12–46 % of the frames; the result is labelled "poor". The SOP asks for photos or a slow video.
  • Scale. Photos do not fix real-world size: the model is labelled "scale unknown" until the user enters one known length. The fallback assumption (1.4 m phone height) was off by −5 % to +90 %, so it is never shown as metric.
  • Navigation is not validated. No scene meets the route criteria (best: 4 routes, 0 collisions, 8 pairs missed); walking paths are shown only as unverified (Round 2: floor completion with human verification, ARCH-030).
  • Compute. CPU only: Preview 4–40 s per image, Standard 80–100 s per 24 MP photo. A 44-photo hall at Standard needed 11.2 GB and exceeded the time limit (failed, kept); Standard is now capped at 4 M faces and the Studio advises Preview first above 40 photos.
  • Licences. OpenMVS is AGPL-3.0 (used unmodified as an external program, never bundled); ETH3D and ARKitScenes are non-commercial: their derived models are not published.
